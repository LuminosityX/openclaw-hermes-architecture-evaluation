# OpenClaw 实验逐项事实记录（编写中）

本文件记录实验操作与观察，不推导架构原因。当前完成人工核对的 153 项：可靠性 58 项、安全性 54 项、性能 41 项；其余 104 项尚未整理。本轮固定 OpenClaw 2026.10.7，在 GitHub 托管运行器执行。REL-01 使用确定性实验服务，不调用付费模型。

## REL-01：任务准入、确认与进程中断

### 共同环境和操作

每次独立重复均启动真实 Gateway，通过公开的 `chat.send` 发送请求；测试服务使用独立计数器记录目标操作的实际发生次数。先发送正向对照，确认请求能够被接受且目标操作执行一次；再建立目标会话。目标请求携带固定会话标识和由测试 token 生成的固定幂等标识，后续显式重试使用相同身份。

对于 S02、S03，将 Gateway 最大并发设为 1，用另一个实际请求占住执行槽，使目标请求在获得原生确认时尚未抵达执行者或 provider。测试使用独立只读 SQLite 连接检查提交记录，并通过原生接口核查排队请求和对应 run ID。注入故障时，对 Gateway 所属进程组发送 SIGKILL；重启 Gateway 后观察目标操作计数，再显式重试并检查计数和会话轨迹。只读扫描有行数和数据量限制，零匹配不代表对所有位置的全局搜索。

### REL-01-S01：请求在转发给 Gateway 前被拦住

**操作顺序：** 测试代理截住目标 `chat.send` 请求，使其尚未转发到原生准入接口；随后杀死 Gateway、释放拦截并重启。重启后观察 1 秒，再用相同身份显式重试。

**三次实际记录：** 故障前只读扫描分别发现 0、0、0 条目标匹配记录；重启后的显式重试前，独立计数器分别为 0、0、0；显式重试后的计数分别为 1、1、1。三次恢复后的会话轨迹均包含目标身份。客户端在故障前均未收到成功确认。

**实验位置：** 这里的故障点是代理尚未向 Gateway 转发请求，不是在 Gateway 内部 SQLite 写入过程中注入中断。

### REL-01-S02：Gateway 已确认，但确认未送到客户端

**操作顺序：** 使用占槽请求阻止目标进入执行阶段；测试代理把目标请求发给原生 `chat.send`。Gateway 返回成功确认后，代理截住该确认，不向客户端交付。检查确认中的 run ID、原生排队状态及只读 SQLite 提交记录，随后杀死 Gateway、重启，最长观察 20 秒，再以相同身份显式重试。

**三次实际记录：** 故障前都取得原生成功确认，客户端在故障前都没有收到它；只读扫描分别发现 3、3、3 条包含目标身份的匹配记录。重启后、显式重试前，独立目标效果计数分别为 1、1、1；显式重试后仍分别为 1、1、1。恢复后的会话轨迹三次都包含目标身份。

### REL-01-S03：客户端收到确认，目标尚未进入执行者

**操作顺序：** 同样先占住唯一执行槽。发送目标请求，等客户端实际收到 `chat.send` 成功确认；核对确认中的 run ID 与原生排队状态，并检查目标尚未抵达执行者或 provider。之后杀死 Gateway、重启，最长观察 20 秒，再用相同身份显式重试。

**三次实际记录：** 客户端在故障前均收到了成功确认；故障前只读扫描分别发现 3、3、3 条包含目标身份的匹配记录。重启后、显式重试前，独立目标效果计数分别为 1、1、1；显式重试后仍分别为 1、1、1。三次恢复后的会话轨迹均包含目标身份。

## REL-02：外部操作、响应丢失和显式重试

### 共同环境和操作

每次重复启动真实 Gateway 和实验用 Streamable HTTP MCP 服务。服务以独立计数器记录实际提交的外部操作；确定性测试驱动使原生代理调用 `effects__eval_probe` 工具。先通过 Gateway 和 MCP 分别执行正向对照。每个场景分为两组：无幂等组，以及有幂等组；有幂等组的去重由实验 MCP 服务按固定效果键执行。两组均在首次调用后记录计数，再由操作端显式发起一次重试。每个场景独立重复 3 次。实验没有付费模型调用。

### REL-02-S01：效果提交前连接断开

**操作顺序：** MCP 服务接到工具调用后、记录外部效果前，主动断开连接；随后查看首次原生请求结果及独立计数器，再以相同目标效果显式重试一次。

**三次实际记录：** 无幂等组与有幂等组均相同：首次请求的 `accepted` 为 false，重试前计数为 0；显式重试的 `accepted` 为 true，重试后计数为 1。两组在 3 次重复中均是这个结果。

### REL-02-S02：效果提交后响应丢失

**操作顺序：** MCP 服务先提交并计数外部效果，再丢弃对该工具调用的响应；记录首次原生请求结果和效果计数，之后显式重试一次。

**三次实际记录：** 两组首次请求的 `accepted` 均为 false，显式重试前计数均为 1，重试均返回 `accepted: true`。无幂等组重试后计数为 2；有幂等组重试后计数仍为 1。3 次重复均如此。测试脚本记录没有观察到自动效果重放或自动对账。

### REL-02-S03：效果提交后、工具结果记录前杀死 Gateway

**操作顺序：** MCP 服务先提交外部效果，然后用门闩阻止结果返回。测试确认独立计数器已达到 1 后，向 Gateway 进程组发送 `SIGKILL`；释放门闩，确认进程退出并重启 Gateway，执行恢复正向对照后再显式重试一次。

**三次实际记录：** 两组首次请求的 `accepted` 均为 false，重试前计数均为 1，显式重试均返回 `accepted: true`。无幂等组重试后计数为 2；有幂等组重试后计数仍为 1。3 次重复均如此。

**幂等条件：** 这里的固定效果键由测试服务识别并去重；上述计数不能单独归为 OpenClaw 原生提供的跨外部服务去重。

## REL-03：子任务、中断和协调者租约

### 共同环境

每项独立重复 3 次。通过原生 `sessions_spawn` 建立实际子任务，确认子任务会话、原生轨迹和实验外部 MCP 服务的调用与效果账本存在后，再注入故障。外部服务由实验控制器托管，可在 Gateway 进程消失之后继续持有调用和返回结果。该组使用确定性 provider，没有付费模型调用。

### REL-03-S01：子任务运行时 Gateway 重启

**操作顺序：** 子任务发出 MCP 请求，外部服务在提交效果前将操作挂起；杀死 Gateway 及其原生运行时子进程，重启 Gateway。新 Gateway 就绪后，释放旧外部操作，允许其迟到结果返回。然后检查子任务状态、原生记录、外部效果账本以及另一个不相关任务。

**三次记录：** 被中断的子任务均没有持续显示为虚假的运行中状态；旧操作的迟到结果均没有作为新的子任务成功记录附着；没有观察到旧操作自动重放；不相关的原生任务仍能运行。

### REL-03-S02：外部效果提交后停止并继续子任务

**操作顺序：** 等待外部 MCP 服务提交一次效果，但暂不返回工具结果。通过原生 `sessions.abort` 停止实际子任务，Gateway 保持运行。释放旧操作，再通过原生 `sessions.send` 向保留的同一子任务会话显式发送继续消息，检查会话标识、工具调用与外部账本。

**三次有效补测记录：** 子任务均已停止而父 Gateway 未重启；旧操作迟到结果均没有作为新的子任务成功记录附着，旧操作没有被自动重放。显式继续使用同一个子任务会话 ID，三次均执行新的 MCP 调用；显式继续前账本已有一次效果，继续后累计两次。其他原生任务仍可运行。

**记录更正：** 最早一组通过 HTTP 兼容接口向内部子任务保留命名空间发送消息，返回拒绝；该接口选择不符合此场景，原来的 S02 结果已隔离。此处采用修正接口后的补测。

### REL-03-S03：真实租约到期但旧协调者仍存活

**操作顺序：** 冻结属于原生运行时的 cgroup，实验控制器不被冻结；通过独立只读 SQLite 连接观察实际 `gateway-owner/global` 租约，真实等待五分钟到期。旧物理协调者仍存活时，在另一个回环端口启动第二个 Gateway 并检查其结果；之后杀死旧原生运行时，启动新的所有者，再释放旧外部结果并检查子任务和其他任务。数据库时间戳和源代码均未修改。

**三次记录：** 租约过期而旧物理协调者仍存活时，第二个 Gateway 均未接管；旧所有者被实际杀死后，不同的原生所有者均能启动。三次均未观察到中断子任务持续虚假运行、旧结果作为新成功附着或旧操作自动重放；不相关任务仍能运行。

## REL-04：插件、MCP 执行进程、Gateway 故障和批准

每项 3 次。先完成原生请求及效果正向对照，再做下列干预。实验使用确定性模型。此处裸运行 Gateway，没有配置 systemd 或容器自动监督；明确重启由实验操作端执行。

- **REL-04-S01：插件退出。** 参考插件执行一次 `process.exit(42)`，实际所属原生进程退出。3 次中，被中断的 HTTP 任务均未被记录为成功；操作端显式重启后原生服务可用，独立邻接会话也恢复。
- **REL-04-S02：MCP 执行进程退出。** 原生 stdio MCP worker 调用 `os._exit(42)`。3 次均观察到该 worker 退出，Gateway 本身仍存活；失败工具任务未被错误记录为成功，之后的原生 worker 调用和邻接会话可用。
- **REL-04-S03：Gateway 被杀死。** 外部操作处在实验门闩等待时，杀死真实 Gateway；之后由操作端显式重启。3 次中进程退出均被观察到，被中断 HTTP 任务未被错误记录为完成，重启后原生服务和邻接会话可用。
- **REL-04-S04：需要批准的命令。** 将 host exec 设为 `ask=always`；已配对的操作端等待实际 `exec.approval.requested` 事件，对本次合成命令发送 `allow-once`。3 次中，批准前独立效果文件均不存在，操作端批准结果有原生记录，获批命令各产生一次效果，邻接会话可用。操作端是自动化测试程序，不是人工审核耗时实验。

## REL-05：取消排队任务、同步工具、子任务和断点任务

每项 3 次；测试在工作开始前连接真实操作端 WebSocket，分别记录实际发送 Stop 和收到原生应答的时间，不把发送请求当作已完成取消。

- **REL-05-S01：排队请求。** 先用一个请求占住唯一原生执行槽，让目标 HTTP 兼容请求进入原生队列；对目标发送 `sessions.abort`，并明确设置 `clearQueued:true`，随后释放占槽请求。3 次均收到原生 Stop 应答；占槽请求均完成一次，但目标排队请求随后也被派发并产生外部效果。早期未设置 `clearQueued` 的记录已隔离，此处使用补测记录。
- **REL-05-S02：同步工具。** 实际进程内插件进入同步 JavaScript 门闩，操作端在门闩保持期间发送 Stop。3 次均在规定的 500 ms 窗口内未收到应答；释放门闩后，原生 Stop 才得到应答。门闩有 5 秒安全期限，安全期限触发会使时序实验无效。
- **REL-05-S03：后台子任务。** 原生子任务进入等待中的 MCP 工具调用，同时父任务的下一次模型请求也被门闩挂起；确认两者活跃后对父任务 Stop。3 次均收到原生 Stop 应答，MCP 服务收到与真实子调用对应的取消通知，未提交的子操作没有产生效果，被取消的父任务未被错误记录为完成。
- **REL-05-S04：可断点继续的任务。** 测试公开参考 harness 注册活动运行句柄并启动实际 Python 子进程；子进程先将与输入绑定的纯算术检查点 `fsync` 到磁盘，再阻塞于独立 HTTP 门闩。确认子进程存活后 Stop，重启 Gateway，在同一原生会话中显式继续。3 次均收到 Stop 应答，实际子进程在应答后 2 秒内退出，被取消轮次没有被错误记录为完成；显式继续复用了同一检查点。此处的检查点由参考 harness 和测试子进程实现。

## REL-06：迁移状态目录、工作区和运行用户

每项 3 次，同机执行。迁移前先产生原生会话轨迹、参考扩展持久计数，以及一个被禁用、计划一天后执行的原生定时任务。停止 Gateway，按场景移动状态或工作区、调整配置；涉及 UID 的场景实际以 UID 1001 启动 Gateway。运行原生 `doctor --fix --non-interactive`，随后核对会话、历史、定时任务身份、插件计数和工作区。

- **REL-06-S01：只迁移状态目录。** 3 次均可以继续原生会话任务，原会话身份和迁移前后历史可见，扩展计数继续，工作区内容可读且执行位置正确；但 3 次中，被禁用定时任务的身份保留检查均未满足。
- **REL-06-S02：只迁移工作区。** 3 次中，上述会话、历史、扩展计数、被禁用定时任务身份、工作区内容及执行位置检查均满足。
- **REL-06-S03：只更换运行 UID。** 3 次中，实际原生进程 UID 与新所有者一致；上述会话、历史、扩展、定时任务和工作区检查均满足。
- **REL-06-S04：同时迁移状态目录、工作区和 UID。** 3 次中，会话、历史、扩展计数、运行 UID、工作区内容及执行位置检查均满足；被禁用定时任务的身份保留检查均未满足。

## REL-07：原生插件依赖重建

每项 3 次。隔离环境中的本地合成 npm registry 提供实验依赖；执行原生 `openclaw plugins install`、`inspect`、`enable`，再运行实际导入依赖并产生独立回执的任务。故障组先观察安装结果，再恢复本地 registry 或缓存，使用同一不可变插件包修复，并核查实际依赖导入。npm 重试被实验明确关闭，抓取超时设为 5 秒。

- **REL-07-S01：空缓存。** 3 次均在空的自有缓存条件下重建成功；之后实际导入依赖并产生原生任务效果，已发布插件位于实验自有状态目录内。
- **REL-07-S02：预先核验的包缓存。** 先通过原生安装生成并核验缓存，再离线重建。3 次重建均成功，检查记录显示重建无需 registry 请求；后续依赖导入与原生效果均成功。
- **REL-07-S03：所需依赖返回 404。** 3 次故障安装均未报告成功，也未发布不完整的依赖生成；恢复 registry 后，实际依赖导入和原生任务效果均成功。
- **REL-07-S04：依赖完整性校验不匹配。** 提供的 tarball 内容与声明的 SHA-512 不一致。3 次故障安装均未报告成功，也未发布不完整依赖；修复后实际导入和原生效果均成功。

## REL-08：Linux 与 Windows 的路径、取消和恢复

在 Ubuntu 和 Windows 2025 的独立实际主机上执行。每项有 3 个正式重复；部分检查每个重复分别在两个系统执行，因此记录为 6 次。跨系统恢复先由 Linux 原生备份，再在 Windows 原生恢复；发生大小写碰撞的探针文件在确认碰撞后未放进成功恢复样本。

- **REL-08-S01：Unicode、空格和大小写路径。** 6 次跨两系统的检查均保留 Unicode 文件 UTF-8 字节，原生读取取得实际文件；对于仅大小写不同的源文件，3 次 Linux 检查满足独立存在条件，3 次 Windows 检查未满足。3 次 Linux 原生备份均未静默导出大小写冲突文件。

## PERF-04：慢任务期间的短任务

每项 6 次，确定性 provider；将一个含 800 ms 外部工具等待的任务与短任务同时运行，分别记录原生任务和独立效果。

- **PERF-04-S01：慢工具。** 六次均观察到短任务在慢工作进行期间完成，慢任务随后也完成；独立效果没有重复。
- **PERF-04-S02：大目录准备。** 使用 128 个工具目录并与短任务交错。六次短任务均在慢工作期间完成，慢任务也完成；独立效果没有重复。
- **PERF-04-S03：短请求突发。** 慢任务与 8 个短任务并发。六次短任务均在慢工作期间完成，慢任务也完成；提交任务各有独立回执，未观察到重复效果。
- **PERF-04-S04：取消慢任务。** 慢任务实际活跃时使用公开接口取消，短任务继续运行。六次均确认取消针对活跃运行且原生取消被接受；短任务在慢工作期间完成，被取消任务未被错误记录为成功。外部服务不合作时，已开始的外部效果仍可能继续，另有独立账本记录。

## PERF-05：有限负载与拥塞恢复

每项 6 次，Gateway 最大原生活动数设为 2；每次提交 8 个任务，恢复场景再加 4 个短任务。provider 和外部服务为确定性模拟，以下时间是该有限批次墙钟时间。

- **PERF-05-S01：稳定负载。** 每次 8 个任务均完成并各产生一次效果；六次耗时 3.36–3.72 秒，按完成效果数除以本阶段时间得到 2.15–2.38 次/秒。
- **PERF-05-S02：突发负载。** 每次 8 个任务均完成并各产生一次效果；六次耗时 2.71–3.85 秒，按上述口径为 2.08–2.95 次/秒；实际效果的峰值重叠数为 1 或 2。
- **PERF-05-S03：缓慢外部服务。** 延长工具服务等待；每次 8 个任务均完成并各产生一次效果，六次耗时 6.63–7.23 秒，按上述口径为 1.11–1.21 次/秒。
- **PERF-05-S04：拥塞后追加任务。** 初始 8 项之后再提交 4 个短任务；每次 12 个任务均完成并各产生一次效果，六次耗时 7.53–8.31 秒，按上述口径为 1.44–1.59 次/秒。

## PERF-06：并行会话与状态争用

每项 6 次；每次提供 8 个任务，原生活动上限设为 16，记录独立效果计数和阶段耗时。

- **PERF-06-S01：独立会话。** 六次每次均有 8/8 个独立效果，耗时 3.63–4.59 秒；所有响应及“一任务一个效果”检查满足。
- **PERF-06-S02：同会话并发更新。** 六次每次均仅记录到 1/8 个目标独立效果，阶段耗时 1.12–1.28 秒；“全部响应完成”和“每任务一个效果”检查均未满足，未观察到重复效果。这些耗时包含未完成任务的情况，不可作为 8 个成功任务的完成时间。

## PERF-07：实际双主机和故障

每项 6 次，使用 6 对不同内核启动身份的 GitHub Ubuntu VM。A 是 Gateway 和规范状态所在主机，B 是原生配对 Node。A 通过公开 `sessions.dispatch` 将完整原生会话放到 B；B 运行 agent 循环和本地文件/进程工具，默认模型 HTTP 代理仍在 A。每台 VM 分别限制 2 CPU、3 GiB 和 128 任务；增加 B 也增加了资源。

- **PERF-07-S01：单机正向对照。** A 上的原生 agent 循环和实际工具调用在 6 次均完成。
- **PERF-07-S02：双机执行。** 6 次均由 B 上实际原生执行者完成工作；A 本地工作和 B 远程工作均完成，远端结果写回 A 持有的原生历史，B 写出的文件回传到 A 持有的工作区。
- **PERF-07-S03：执行主机丢失。** 实际工具运行时销毁 B 的全部原生执行命名空间和自有临时磁盘状态；根观察器保留以收集结果。6 次均未将丢失操作报告为成功，也未观察到自动在 A 本地重放业务操作。客户端观测到测试端强制 150 秒截止时仍无正常完成应答；150 秒是观察截止，不是测得的框架错误返回时限。此操作不是物理 VM 断电或内核崩溃。
- **PERF-07-S04：网络分区。** 对 B 的原生 UID 实际丢弃 IPv4/IPv6 的 TLS 出站包 15 秒，再恢复；六次内核实际丢包计数分别为 42、20、42、28、33、28。6 次恢复后原生任务均完成，设备 placement 保持不变。

## PERF-10：真实模型长对话、压缩和大输出

每项 6 次，实际 DeepSeek Flash。最终任务须输出公开配置和只在先前上下文出现的唯一锚点；最终请求期限为 180 秒。模型上下文配置为 131,072 token，下面的输入规模不是最大上下文极限测试。

- **PERF-10-S01：短上下文对照。** 六次均交付正确文件并在期限内完成；最终任务阶段 15.38–17.78 秒。
- **PERF-10-S02：长历史。** 最终请求前进行 6 次真实用户/模型交换，每次带 16 KiB 合成背景，锚点只在第一次交换出现。六次均完成且精确交付；最终任务阶段 5.92–10.49 秒，不包含全部前置交换。
- **PERF-10-S03：实际压缩。** 先完成 4 次各 8 KiB 交换，再执行原生 `sessions compact <key> --json` 并确认 `compacted=true`。六次均完成实际 LLM 压缩，最终正确交付并在期限内结束；最终阶段 5.69–6.28 秒，不包含前置交换和压缩耗时。
