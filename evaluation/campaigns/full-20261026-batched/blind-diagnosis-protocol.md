# OBS-03: held-out native faults and a frozen record consumer

Four frozen scenarios each run three fresh independent native units after whole-family calibration. Their actual native mechanisms are separately validated: committed input with a lost client ACK (REL-01), active parent/child cancellation (REL-05), an actual approval/revocation window (SEC-06) and a remote effect whose native result is lost before checkpointing (REL-02). The nested original native records and independent truth remain in raw hosted evidence; earlier formal observations are never reused or promoted.

The deterministic reader in `blind_native_reader.py` accepts only a fixed native-record channel schema. Native request/response IDs, session relationships, approval records, actual client transport observations, public histories and bounded native SQLite committed-row evidence may enter. The fault label, independent remote effect ledger and intervention gates cannot. Synthetic `PILOT_*` labels are replaced by stable opaque aliases that preserve cross-record identity. User prose is not parsed into authoritative structured records. An input hash and the original nested record allow exact reconstruction of what the reader saw.

The reader first makes a fault-category diagnosis, then reports whether its selected native joins establish the specific boundary. It distinguishes a written request from a native response and a saved mode from effective dispatch policy. A failed native MCP reply never proves that its remote effect did or did not commit. The held-out truth is compared only after diagnosis. Missing records and causal links therefore produce unknowns or failed diagnostic acceptance observations, not invented certainty.

This is a registered deterministic record-consumption experiment, not a general human-debugging or model-capability benchmark and not proof that no expert could interpret other native fields. A failure may reflect this reader or its selected record surface. The later unified architecture analysis must inspect the actual native source and records before attributing any limitation to OpenClaw's design.

The approval case uses the already validated owned kernel file-open gate. Only the evaluator receives kernel-gate capabilities; every native Gateway drops its capability bounding set before Node executes. All faults, traces and at most 128 MiB temporary state remain on disposable GitHub-hosted workers. No paid model is called and no runtime or raw trajectory is stored locally.
