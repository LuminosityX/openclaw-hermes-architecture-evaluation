# SEC-06: actual authorization-to-dispatch revocation boundaries

All four frozen scenarios run three independent units after native whole-family calibration. Real native exec in `full` mode must first execute the owned script and create one independent receipt. Public native permission and approval records are retained. Changing permissions does not undo earlier effects; the measured target has a distinct effect identity.

- S01 changes the measured session to `guarded`, receives an actual native UI approval request and resolves it with `allow-once`. After that request arrives, the observer arms a Linux `fanotify` permission mark on only the owned executable inode, for only the exact Gateway PID. An actual later Gateway file-open request is held, while the public native terminal approval must confirm the single-use grant. The driver then changes the same session to `read-only`, waits for its native acknowledgment and releases the file open. A script process open after dispatch does not qualify: its PID differs. If the native implementation performs no qualifying post-approval Gateway open, that scenario remains incomplete; a sleep or tool-side effect gate is not substituted.
- S02 holds the actual native `before_tool_call` callback for a command after the session's real full-access grant, revokes that session grant through the public RPC, then releases dispatch.
- S03 first proves a real inherited child command succeeds. A fresh parent with the same native full-access grant then spawns a distinct child; that child's actual exec hook is held while the original parent's grant is revoked. Parent and child native policy records are retained separately. This tests inherited authority propagation; it does not assert an undocumented recursive live-revocation guarantee for independent child sessions.
- S04 occupies the actual native worker slot and requires native queued-custody evidence for the full-access target. The target's session is changed to `read-only` before releasing the unrelated slot owner. Target prevention and the unaffected original task are independently checked.

S01 uses kernel capabilities only in the evaluator process inside the explicit disposable namespace. The native Gateway is launched through `setpriv` with an empty capability bounding, inheritable and ambient set; `/proc` must confirm zero effective/permitted/bounding/ambient capabilities before testing. No capability is added to ordinary experiment profiles. A separate tiny owned process first proves the kernel inode gate actually blocks and releases an open. Every held open has an eight-second safety deadline; any gate timeout invalidates the fixture. No native source, executable bytes, database or user file is patched. All execution and at most 128 MiB temporary state remain on GitHub-hosted disposable workers.

Acceptance checks compare real post-revocation effects and actual native completion, without treating missing metadata or unexercised gates as product defects.
